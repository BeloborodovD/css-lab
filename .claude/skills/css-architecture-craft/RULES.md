# CSS Architecture — Non-Negotiable Rules

Канонический свод правил архитектуры стилей этого репозитория: токены, именование,
каскад, границы глобального и локального, допустимые литералы, принудительный контроль.
Значения здесь взяты **из кода**, а не из общих соображений — копируются буквально.
Все пути даны от корня репозитория.

**Движение — вне этого свода.** Кривые, длительности, физика входа/выхода, прерываемость,
`prefers-reduced-motion` описаны в `.claude/skills/ui-motion-craft/RULES.md` и живут в
`styles/base/motion.css`. Здесь про motion сказано ровно одно: это отдельный слой токенов,
он подключается первым и в компонентах не дублируется. При расхождении по вопросам
движения побеждает ui-motion-craft.

Читается целиком перед первой строкой CSS в этом репозитории.

## §1. Таксономия токенов

### 1.1. Семейства префиксов

Все токены определяются в `styles/base/variables.css` (кроме явно указанных исключений).
Компонент видит только семантический слой — примитивные значения ему недоступны по правилу.

| Префикс | Что означает | Шаблон имени | Где определён |

### 1.2. Четыре слоя — порядок обязателен

1. **Примитив.** Литеральное значение (`#18181b`, `12px`, `cubic-bezier(...)`).
   Живёт **только** в `styles/base/variables.css` и `styles/base/motion.css`.
   Компонент примитивов не видит и не объявляет.
2. **Семантика.** Имя роли поверх примитива: `--color-text-muted`, `--space-4`,
   `--shadow-lg`. Это единственный слой, с которым работают `styles/components/*.css` и
   `styles/pages/*.css`.
3. **Бренд / тема.** `styles/themes/veza.css`, `uralelectro.css`, `hemah.css` перекрывают
   семантику под бренд (`--color-accent*`, `--color-info*`, `--color-highlight*`,
   `--font-sans`, `--font-display`, `--brand-logo*`, `--brand-plate-bg`,
   `--color-accent-paper`); тёмная база — блок `.dark` в `variables.css` плюс
   `styles/themes/dark.css`; предпочтения пользователя (`prefers-contrast: more`,
   `forced-colors`, `prefers-reduced-transparency`) — `styles/base/contrast-preferences.css`
   последним. **Компонент о брендах не знает**: селектор `[data-brand="…"]` внутри
   `styles/components/*.css` — дефект.
4. **Локальный слой компонента.** Переопределение семантического токена на самом блоке —
   легальный и предпочтительный приём, когда контекст меняет палитру целиком.
   Каноническая идиома — «бумажная палитра»: `styles/layout/print-sheet.css` (блок
   `[CONFIG:paper-palette]`), `styles/components/spec-sheet.css`,
   `styles/components/code-panel.css`, печатный блок `styles/components/layout.css`.
   Правило: локальный слой **переопределяет существующие имена**, но никогда не заводит
   новых глобальных.

### 1.3. Когда разрешено заводить новый токен

Все три условия одновременно:

1. Ни один существующий семантический токен по смыслу не подходит (не «подходит, но хочется
   на 4% темнее» — это повод взять соседний по шкале).
2. Значение будет использовано **минимум в двух местах** ИЛИ это документированная
   константа раскладки (как `--header-h`, `--drawer-w`, `--tooltip-max-w` — у последнего
   в `variables.css` записано обоснование ширины).
3. Имя ложится в существующее семейство и шаблон из таблицы 1.1.

Порядок добавления — без пропусков:

1. Объявить в `styles/base/variables.css` в **светлом** блоке `:root`.
2. Объявить в блоке `.dark, [data-theme="dark"]`.
3. Продублировать в зеркало `@media (prefers-color-scheme: dark)` — в этом файле зеркало
   **полное**, и в нём стоит явное предупреждение: «Правишь `.dark` — правь и здесь».
   Пропуск шага даёт нечитаемые цвета при системной тёмной теме без класса.
4. Если значение зависит от бренда — перекрыть во **всех трёх** темах
   (`styles/themes/veza.css`, `uralelectro.css`, `hemah.css`), включая их блоки
   `.dark[data-brand=…]` и `@media (prefers-color-scheme: dark)`.
5. Цвет — посчитать контраст с фоном, на котором он появится, и записать значение
   в комментарии рядом (принятая в `variables.css` форма: `/* 7.9:1 на #18181b, AAA */`).

Токен, объявленный только в светлой теме, — дефект, **кроме** намеренно неинвертируемых:
`--color-accent-paper`, `--brand-plate-bg`, `--brand-logo-paper`, `--color-scrim-light`,
`--color-on-scrim`. У каждого из них в коде записано, почему он не инвертируется.

### 1.4. Токены-сироты

Объявленный токен без единого потребителя — дефект: он выглядит как контракт, но ничего не
держит, и следующий агент строит на нём решение.

Проверка (bash + ripgrep, из корня репозитория):

```bash
for t in $(rg -o -- '^\s*(--[a-z0-9-]+):' -r '$1' styles/base/variables.css styles/base/responsive.css | sort -u); do
  n=$(rg -c --no-filename -- "var\($t[,)]" styles js *.html pages 2>/dev/null | paste -sd+ - | bc)
  [ -z "$n" ] && echo "orphan: $t"
done
```

PowerShell-эквивалент:

```powershell
Select-String -Path styles/base/variables.css,styles/base/responsive.css -Pattern '^\s*(--[a-z0-9-]+):' |
  ForEach-Object { $_.Matches[0].Groups[1].Value } | Sort-Object -Unique | ForEach-Object {
    $hits = Select-String -Path styles/**/*.css,js/*.js,main.js,*.html,pages/*.html -Pattern ("var\(" + [regex]::Escape($_) + "[,)]") -List
    if (-not $hits) { "orphan: $_" }
  }
```

На момент написания свода сироты в репозитории: `--t-instant`, `--z-base`, `--lh-loose`,
`--space-24`, `--icon-size-lg`, `--max-prose-w`, `--breakpoint-*` (вся шкала — она
документация, см. §5.4). Их удаление или подключение — отдельная работа; новых сирот
создавать нельзя.

## §2. Закон BEM: `--modifier` против `is-*`

### 2.1. Блок, элемент

- **Блок = имя файла.** Один компонент — один файл `styles/components/<block>.css`,
  и все селекторы файла начинаются с `.<block>`. Файл `picklist.css` описывает `.picklist`
  и ничего больше.
- **Элемент — `__name`**, ровно один уровень вложенности имени. Составное имя элемента
  пишется через дефис, а не вторым `__`: `.picklist__option-desc`,
  `.print-sheet__running-foot` — не `.picklist__option__desc`.
- Файл обёрнут тегами `[BLOCK:component.<block>]` / `</BLOCK:component.<block>>`
  (или `[CONFIG:…]` для слоёв тем и страниц) — это grep-цели, имена стабильны.

### 2.2. Центральное правило (то, что агенты до сих пор угадывали)

> **`--модификатор` — это ВАРИАНТ, который автор разметки выбирает в момент написания HTML.
> Он неизменен в течение жизни элемента.**
> **`is-*` — это СОСТОЯНИЕ, которое переключает JS во время работы страницы.**

Примеры вариантов из кода: `.picklist__panel--columns` (многоколоночная панель — решение
верстальщика по ширине поля), `.picklist__panel--sheet` (мобильный bottom-sheet),
`.hub-card--invert`, `.hub-card--soon`, `.brand-mark--mono`, `.btn-primary`/`.btn-danger`
(легаси-форма модификатора без двойного дефиса — см. 2.4).

Примеры состояний из кода: `.is-open` (`picklist`, `drawer`, `accordion`, `user-menu`,
`presence-strip`, `swatch-picker`, `combobox`), `.is-filtered`, `.is-selected`,
`.is-active`, `.is-removing`, `.is-entering`, `.is-copied`, `.is-visible`, `.is-disabled`,
`.is-correct`, `.is-wrong`, `.is-near-limit`, `.is-over-limit`, `.is-hidden`.

### 2.3. Следствия — проверяемые

1. **`is-*` без JS-сеттера — дефект.** У каждого состояния обязан быть код, который его
   ставит и снимает (`main.js`, `js/*.js` или инлайновый скрипт страницы). Если сеттера нет,
   возможны ровно две правки: либо написать сеттер, либо это на самом деле вариант — тогда
   переименовать в `--modifier`. Проверка: `rg "is-имя" main.js js *.html pages`.
2. **JS никогда не трогает класс с `--`.** `classList.add/remove/toggle` с именем,
   содержащим `--`, — дефект по определению: раз значение меняется во времени, это
   состояние, и имя должно начинаться с `is-`. Обратная сторона: CSS-комментарий вида
   «класс ставит JS» рядом с `--`-модификатором — тоже дефект (в репозитории такой есть,
   см. §2.6).
3. **Состояние, у которого уже есть нативный носитель, классом не дублируется.**
   `:disabled`, `[open]`, `:checked`, `aria-expanded`, `[data-drag-over]` стилизуются
   напрямую; класс заводится, только когда нативного атрибута нет.
4. **Состояние всегда стилизуется на блоке или его элементе**, а не глобально:
   `.picklist.is-open .picklist__panel`, а не `.is-open .panel`. Голый `.is-open` в
   селекторе — дефект: имена состояний намеренно короткие и пересекаются между компонентами.

### 2.4. Легаси-двойники и направление миграции

В репозитории живут два дореформенных именования состояний:

- дубли: `.combobox.open` рядом с `.combobox.is-open`
  (`styles/components/combobox.css`, `main.js` ставит **оба** класса), `.dropdown.open`,
  `.combobox-option-selected` + `.selected`, `.highlighted`;
- состояния без префикса: `.chip-active`, `.dropdown-item.active`, `.sidebar.resizing`,
  `.toast-enter` / `.toast-exit`, `.file-dropzone.drag-over`, `.file-item-uploading`,
  `.file-item-success` / `.file-item-error`, `.btn-loading`.

Направление одно: **канон — `is-*`**. Правила миграции:

1. Новых дублей не создавать: в новом коде состояние существует в единственном написании.
2. При касании файла добавить `is-`-селектор рядом со старым (через запятую), JS на время
   перехода ставит оба класса.
3. Старое написание удаляется только вместе с последним потребителем в разметке, `main.js`
   и `e2e/smoke.e2e.spec.ts` — одним коммитом, иначе смоук краснеет.
4. Варианты, выраженные легаси-формой без `--` (`.btn-primary`, `.btn-ghost`, `.chip-filled`,
   `.file-icon-pdf`), переименованию **не подлежат**: это публичный контракт классов,
   на который завязаны витрина, тесты и уже отредизайненные проекты. Они читаются как
   модификаторы, к ним применимо правило «JS их не трогает».

### 2.5. Страничные префиксы: когда класс принадлежит странице, а не компоненту

Каждая страница подключает свой файл `styles/pages/<name>.css` с уникальным префиксом:
`.hub-`, `.catalog-`, `.ds-` (datasheet), `.dash-` (dashboard), `.fp-` (form),
`.pf-` (print-forms), `.ral-` (ral-colors), `.login-` (login).

Класс принадлежит **компоненту**, если верны все три пункта: он переиспользуем на разных
страницах; у него есть собственное поведение или анатомия; он показан на витрине
`components.html` и имеет паспорт (см. регламент шага 03 в `pipeline/steps/03-library-first.md`).

Класс принадлежит **странице**, если он описывает раскладку именно этой страницы (грид,
липкая колонка, отступы секций), одноразовую композицию готовых компонентов или
страничные декорации.

Жёсткие следствия:

- **Страничный файл не имеет права объявлять селекторы вне своего префикса.** Правило
  записано в шапке `styles/pages/catalog.css` и распространяется на все страницы.
- Подстройка компонента со страницы — **только** через переопределение токенов на
  контейнере страницы (слой 4 из §1.2), никогда не переписыванием внутренностей блока.
- Если страничный класс понадобился второй странице — это сигнал, что он был компонентом.
  Переезд в `styles/components/` идёт по регламенту шага 03 (витрина, e2e, паспорт),
  а не копированием.

### 2.6. Известное расхождение

`.picklist__panel--top` в `styles/components/picklist.css` снабжён комментарием «класс ставит
JS, замерив свободное место», но ни `main.js`, ни другой скрипт его не ставят. По §2.3.2
это либо состояние с неверным именем (`is-flipped`), либо мёртвый вариант. Правка — вне
этого свода; повторять приём нельзя.

## §3. Каскад

### 3.1. Как устроено сегодня (честно)

Один бандл — `styles/core.css`, целиком собранный `@import`-ами. Порядок цепочки жёсткий и
значимый:

1. `base/motion.css` — **первым**: единственный источник кривых и длительностей.
2. `base/variables.css` — все остальные токены.
3. `base/fonts.css`, `base/reset.css`, `base/utilities.css`, `base/responsive.css`.
4. `layout/` — `site-header`, `site-footer`, `page-shell`, `print-sheet`.
5. `components/*.css` — около шестидесяти файлов.
6. `themes/` — `dark.css`, затем бренды `hemah.css`, `veza.css`, `uralelectro.css`.
7. `base/contrast-preferences.css` — **последним**: пользовательские предпочтения обязаны
   бить и темы, и бренды.

`base/animations.css` в бандл **не входит** (легаси-зверинец, конфликтует с motion-контрактом):
его подключает отдельным `<link>` только витрина `components.html`.

**Приоритет при равной специфичности сегодня определяется порядком `@import`.** Живой
пример — в самом `styles/core.css`: `components/form-error-summary.css` импортируется
**после** `components/alerts.css` и `components/form-section.css`, потому что это композиция
на `.alert.alert-error`, и его элементы обязаны бить общие правила плашки. Порядок
зафиксирован комментарием прямо над импортом.

**Это хрупко, и так и записано.** Порядок не выражен в самих файлах: перестановка импорта
(например, «отсортируем список по алфавиту») молча ломает композицию, а автор нового
компонента не видит, от кого он зависит.

Правила при работе в текущей схеме:

- Новый компонент — `@import` в конец блока `components`, если он ни от чего не зависит.
- Компонент-композиция — импорт сразу после файла-донора **с комментарием, почему именно
  там** (образец — блок над `form-error-summary.css`).
- Порядок хвоста (`themes/` → `base/contrast-preferences.css`) неприкосновенен.
- Побеждать соседа наращиванием специфичности или `!important` запрещено: `!important`
  в репозитории допустим только там, где он уже принят и обоснован, — переключатели
  видимости печати (`.screen-only`, `.no-print` в `styles/layout/print-sheet.css`) и
  сброс движения в `styles/base/motion.css`.
- Страничные файлы в `core.css` не импортируются никогда: страница подключает их вторым
  `<link>`, и именно это даёт им приоритет над компонентами.

### 3.2. ПЛАНИРУЕТСЯ: переход на `@layer` (не выполнять по ходу другой работы)

Цель — сделать приоритет **декларативным** и убрать зависимость от порядка импортов.

Форма диффа (только `styles/core.css`, содержимое файлов не меняется):

```css
/* первой строкой файла — порядок слоёв, дальше он неизменен */
@layer base, layout, components, themes, pages, overrides;

@import './base/motion.css'      layer(base);
@import './base/variables.css'   layer(base);
/* … */
@import './layout/site-header.css'   layer(layout);
/* … */
@import './components/buttons.css'   layer(components);
/* … */
@import './themes/dark.css'          layer(themes);
@import './themes/veza.css'          layer(themes);
/* … */
@import './base/contrast-preferences.css' layer(overrides);
```

Страничные файлы в бандл по-прежнему не входят; чтобы их место в каскаде стало явным,
каждый `styles/pages/<name>.css` оборачивается внутри себя: `@layer pages { … }`.

Риски, каждый из которых обязан быть закрыт до слияния:

1. **Нераспределённый CSS выигрывает у любого слоя.** Файл, забытый без `layer(…)`, тихо
   получает высший приоритет. Проверка: в `core.css` не остаётся ни одного `@import` без
   `layer(...)`; страничные файлы обёрнуты; `base/animations.css` (подключается витриной
   отдельным `<link>`) — тоже, иначе зверинец начнёт бить компоненты.
2. **Слой не отменяет мышление о порядке внутри слоя.** Композиции вроде
   `form-error-summary` остаются зависимыми от порядка импортов внутри `components` —
   комментарии сохраняются.
3. **`!important` инвертирует приоритет слоёв** (важное правило раннего слоя бьёт важное
   правило позднего). Перед миграцией — ревизия всех `!important`.
4. **Специфичность внутри слоя работает как прежде**: слои разводят конфликты между
   уровнями, а не внутри одного файла.
5. **Совместимость**: `@layer` — Chrome/Edge 99+, Firefox 97+, Safari 15.4+. Ниже —
   деградация в непредсказуемый порядок; целевые браузеры фиксируются до работы.
6. **Гейт**: полный прогон `npx playwright test` плюс ручная сверка каждой страницы в трёх
   брендах и обеих темах — переупорядочивание каскада ломает тихо и точечно.

Миграция выполняется отдельной задачей с отдельным коммитом. Частичный перевод (часть
импортов в слоях, часть нет) хуже текущего состояния.

## §4. Глобальное и локальное

Здесь две разные задачи, которые постоянно путают.

### 4.1. Изоляция имён

Проблема: чужой компонент случайно перекрашивает мой. Индустриальные ответы — хеширование
классов (CSS Modules), атрибуты-скоупы (Vue `scoped`), генерация имён (CSS-in-JS).

**Наш ответ — дисциплина имён, а не инструмент:** блок = имя файла (§2.1), все селекторы
файла начинаются с имени блока, страничные слои живут за своим префиксом (§2.5), состояния
всегда квалифицируются блоком (§2.3.4). Этого достаточно, потому что имена уникальны
проектно, а не глобально-случайно. Плата — обязательность правил; выгода — читаемый DOM,
работающие темы через `[data-brand]`/`.dark` и возможность отдать стили в чужой проект
без сборщика.

### 4.2. Дробление полезной нагрузки

**Доктрина: один кэшируемый `core.css` на весь многостраничный сайт лучше, чем per-page
сборки.** Обоснование измеримо: страниц много, компонентная база общая, вторая и все
последующие страницы забирают стили из кэша браузера; per-page бандлы дают на первой
странице выигрыш в килобайтах и проигрывают на каждой следующей — плюс дублирование общего
слоя в каждом бандле и лишние сетевые раунды.

Из этого следует:

- Общий слой — `styles/core.css`, один `<link>` на всех страницах.
- Страничный слой — второй `<link>` на `styles/pages/<name>.css` со своим префиксом.
- **Намеренное исключение** — `styles/base/animations.css`: не входит в `core.css`,
  подключается только витриной `components.html` как экспонат. Всё, что является демо, а не
  библиотекой, живёт по этой же схеме.
- Дробить файл компонента нужно по смыслу (один блок — один файл), а не по весу.

### 4.3. Поставка библиотеки в чужой проект (vendoring)

Сценарий: вы применяете эту дизайн-систему в собственном проекте, репозитория-донора у вас
под рукой может не быть, а обновляться придётся. Порядок:

1. **Скопировать базовый слой** в свой проект, сохранив имена файлов:
   `styles/base/motion.css` (**первым в вашем каскаде — до всего остального CSS**),
   `styles/base/variables.css`, `styles/base/reset.css`, `styles/base/fonts.css`,
   при необходимости `styles/base/utilities.css` и `styles/base/responsive.css`,
   и обязательно `styles/base/contrast-preferences.css` — **последним**.
2. **Скопировать тему бренда**: `styles/themes/dark.css` + ровно тот файл бренда, который
   вам нужен (`veza.css` / `uralelectro.css` / `hemah.css`). Тема без `dark.css` даёт
   нерабочую тёмную тему.
3. **Скопировать только используемые компоненты** из `styles/components/`. Компонент тянет
   зависимости по композиции: `form-error-summary.css` требует `alerts.css` и
   `form-section.css` и импортируется после них; проверяйте шапку файла — в ней перечислены
   зависимости.
4. **Ассеты**: шрифты (`assets/fonts/*.woff2` вместе с файлами лицензий) и логотипы
   (`assets/logos/*.svg`, включая `-mono-light` варианты). Пути в токенах абсолютные
   (`url("/assets/logos/veza.svg")`) — либо повторите структуру каталогов, либо
   переопределите `--brand-logo*` у себя.
5. **Разметка-минимум на стороне потребителя**: `data-brand` на `<body>`, поддержка класса
   `.dark`, анти-FOUC сниппет в `<head>` (образец — любая страница этого репозитория).
6. **Зафиксировать источник.** Рядом с вендоренными файлами — `VENDORED-FROM-CSS-LAB.md`:
   список скопированных файлов, дата, **точный коммит донора** (`git rev-parse HEAD` в
   репозитории дизайн-системы) и перечень ваших локальных отклонений, если они есть.
   Без записи коммита следующее обновление превращается в ручную сверку глазами.
7. **Локальных правок в вендоренных файлах не делать.** Нужна другая величина —
   переопределите токен у себя (слой 4 из §1.2) отдельным файлом, подключённым после
   вендоренных. Правка внутри копии теряется при обновлении и не возвращается в донор.

Чего не забыть: `motion.css` первым, `contrast-preferences.css` последним, тема + `dark.css`
парой, лицензии шрифтов, запись коммита.

### 4.4. Потребители на React и подобных

- **Импортируйте наш CSS глобально** (один импорт бандла или набора файлов в корне
  приложения). Не превращайте его в CSS Modules: хеширование ломает публичный контракт имён
  (`.btn`, `.is-open`), на который завязаны тесты и разметка, и рвёт темизацию через
  `[data-brand]`/`.dark`, которая работает от предков.
- **Поведение берётся из библиотек** (по вердикту скилла `pick-ui-library`: фокус-ловушки,
  порталы, listbox-семантика), **стили — от нас темой**: библиотечным узлам выдаются наши
  классы или их токены переопределяются нашими. Переписывать поведение вручную ради
  «чистоты стилей» — дефект.
- Состояния библиотеки, приходящие атрибутами (`data-state="open"`, `aria-expanded`),
  стилизуются напрямую по §2.3.3 — плодить зеркальные `is-*` не нужно.

## §5. Белый список литералов

В `styles/components/*.css` и `styles/pages/*.css` любое значение — токен. Закрытый список
исключений ниже; всё, что вне него, — дефект.

**5.1. Физическая геометрия печати в мм и pt.** `width: 210mm`, `min-height: 297mm`,
`padding: 16mm 14mm` в `styles/layout/print-sheet.css`; `@page { size; margin }` страницы;
печатный кегль в пунктах (`font-size: 7pt` в том же файле). Причина: бумага — физическая
величина, миллиметр и пункт не масштабируются вместе с UI-шкалой, и токена для них быть
не должно.

**5.2. Толщина границ — токен, а не «хайрлайн».** `--border-w` (1px), `--border-w-strong`
(2px), `--border-w-thick` (3px) существуют, поэтому `border: 1px solid …` в компоненте —
дефект; правильно `border: var(--border-w) solid var(--color-border)`. Литерал допустим
только для дробных значений, которых нет в шкале (`border-width: 1.5px` у `.spinner-xs`),
и внутри самих определений токенов и теней в `styles/base/variables.css`.

**5.3. Размеры нативных контролов и целей нажатия.** Чекбокс 18px (десктоп) и 22px
(`@media (max-width: 767px)`) — прецедент `styles/components/inputs.css` и
`styles/components/picklist.css`; квадрат мелкой кнопки-цели 24px (WCAG SC 2.5.8) —
`.picklist__toggle`, `.picklist__chip-remove`. Это размеры физического пальца и системного
контрола, а не дизайн-шкала. Для крупной тач-цели 44px есть токен `--touch-target-min` —
предпочитать его.

**5.4. Брейкпоинты в медиазапросах.** `var()` в `@media` не работает по спецификации,
поэтому значения пишутся числом: 479 / 767 / 768 / 1023 / 1024 / 1279 / 1280 px.
Шкала-первоисточник — `--breakpoint-*` в `styles/base/responsive.css` (320/480/768/1024/
1280/1536); `max-width` берётся как соседний `min-width` минус 1px. Изобретать значения вне
этой шкалы нельзя.

**5.5. `transparent`, `currentColor` и `#000`/`#fff` в масках.** Прозрачный контур фокуса —
обязательная идиома forced-colors: `outline: var(--border-w-strong) solid transparent`
плюс `box-shadow: var(--shadow-focus)` (система перекрашивает прозрачный outline в
Highlight, а тень вырезает). `mask: radial-gradient(farthest-side, transparent
calc(100% - 3px), #000 calc(100% - 3px))` в `styles/components/spinner.css` — здесь `#000`
это альфа-канал маски, а не цвет. `border-color: transparent`, `background: transparent`
цветом не считаются.

**5.6. Унаследованные исключения — список закрыт, расширению не подлежит.**
`styles/components/spinner.css`: `.spinner-white { border-color: rgba(255,255,255,0.3);
border-top-color: #fff }` — индикатор поверх произвольного цветного фона (аналогичная пара
в `.btn-primary.btn-loading::before`, `styles/components/buttons.css`).
`styles/components/file-upload.css`: `linear-gradient(transparent, rgba(0,0,0,0.7))` под
подписью превью, `#fff` на ней, `rgba(0,0,0,0.6)` у кнопки удаления поверх фото. Причина
одна: подложка — пользовательская картинка, у неё нет темы и токена. Новые компоненты
подобные случаи решают токенами `--color-overlay`, `--color-scrim-light`, `--color-on-scrim`.

**5.7. Не литералы в смысле этого правила:** `0`, безразмерные множители, проценты,
`fr`, `ch`, `auto`, `vh`/`vw` (`max-height: 50vh` у панели пиклиста), `aspect-ratio`,
процентные `translate` (требование ui-motion-craft §3).

**5.8. «Бумажная палитра» — переопределение токенов на блоке.** Разрешено объявлять
`--color-*` литеральными значениями внутри блока, который принудительно живёт в светлой
палитре (`.print-sheet`, `.spec-sheet`, `.code-panel`, печатный блок `layout.css`) при трёх
условиях: значения **скопированы** из светлой палитры `styles/base/variables.css` без
изобретения новых оттенков; блок сопровождён комментарием, почему палитра фиксирована;
акцент берётся через `--color-accent: var(--color-accent-paper)`, а не подбирается заново.

## §6. Принудительный контроль

Свод подкреплён скриптом `.claude/skills/css-architecture-craft/naming-lint.py` —
PostToolUse-хук той же формы, что `.claude/hooks/motion-lint.py`: читает JSON события из
stdin, реагирует на `Write`/`Edit`/`MultiEdit`, разбирает только что записанный текст,
печатает JSON-решение и всегда выходит с кодом 0. Порядок включения — в `SKILL.md`.

**Блокирует (однозначные нарушения):**

| Проверка | Что ловит | Что предлагает |
| --- | --- | --- |
| (a) цветовой литерал | `#hex`, `rgb()`, `rgba()` в `styles/components/**` и `styles/pages/**` вне белого списка §5 | ближайший семантический токен (`#fff` → `--color-surface` / `--color-text-on-accent`, `rgba(0,0,0,…)` → `--color-overlay`) |
| (b) px вместо токена | `font-size: Npx`, где N совпадает со шкалой `--fs-*`; `padding`/`margin`/`gap` с положительным N из шкалы `--space-*` | точное имя токена |
| (c) модификатор в JS | `classList.add/remove/toggle` с именем, содержащим `--` (файлы `.js`/`.ts`/`.jsx`/`.tsx`) | переименовать состояние в `is-*` (§2.3.2) |

**Предупреждает, не блокируя:**

| Проверка | Что ловит |
| --- | --- |
| (d) состояние без сеттера | новый `.is-*` в CSS, которого нет ни в `main.js`, ни в `js/*.js`, ни в разметке страниц (§2.3.1) |
| (b′) px вне шкалы | `font-size` в px без соответствия шкале — возможен легальный случай (глиф иконки) |
| (a′) токен-литерал | объявление `--color-*: #hex` в компоненте — идиома §5.8, но требует комментария и сверки со светлой палитрой |

Скрипт консервативен намеренно: он молчит на всём, что не является однозначным нарушением,
и не заменяет чтение этого свода. Файлы `styles/components/spinner.css` и
`styles/components/file-upload.css` внесены в список унаследованных исключений (§5.6) и не
проверяются на цвет. Самопроверка: `python .claude/skills/css-architecture-craft/naming-lint.py --selftest`.

## §7. Самопроверка перед сдачей компонента

1. Блок = имя файла; все селекторы файла начинаются с имени блока; элементы через `__`,
   один уровень; файл обёрнут `[BLOCK:component.<block>]`.
2. Каждый `--модификатор` выбирается автором разметки; ни один не переключается из JS.
3. Каждый `is-*` имеет сеттер в JS; ни одно состояние не стилизуется голым `.is-*`.
4. Новых легаси-двойников (`.open` рядом с `.is-open`) не создано; если файл содержал
   старый — рядом добавлен `is-`-селектор.
5. Ни одного цветового литерала, кегля, отступа, радиуса, тени, z-index вне `var()`;
   исключения — только из закрытого списка §5, каждое с комментарием.
6. Границы через `--border-w*`; тени через `--shadow-*`; фокус — `--shadow-focus` плюс
   прозрачный `outline` (идиома forced-colors).
7. Новые токены (если были) объявлены в светлом блоке, в `.dark`, в зеркале
   `@media (prefers-color-scheme: dark)` и во всех трёх темах, если зависят от бренда;
   контраст посчитан и записан в комментарии.
8. Токенов-сирот не добавлено — grep из §1.4 чист.
9. Компонент ничего не знает о брендах: `[data-brand=…]` внутри файла компонента нет.
10. `@import` добавлен в `styles/core.css` в правильное место; если это композиция —
    сразу после файла-донора с комментарием, почему.
11. Страничные стили не попали в `core.css`; страничный файл не выходит за свой префикс,
    а компонент подстроен только через переопределение токенов на контейнере.
12. Мобильный вид проверен на 479/767/1023 px; тач-цели ≥24px, крупные ≥44px.
13. Обе темы (светлая, `.dark`, системная тёмная без класса) и все три бренда проверены
    визуально; печатный вид — если компонент попадает на бумагу.
14. Движение — по `.claude/skills/ui-motion-craft/RULES.md` (его собственный чек-лист),
    ни одной кривой и длительности литералом.
15. `naming-lint.py` и `motion-lint.py` молчат; `npx playwright test` зелёный.
